# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

CarCheck API: NestJS backend for a vehicle marketplace where a buyer can book an **inspector** (mechanic/specialist) to evaluate a car before buying. It's a personal study project focused on clean backend↔frontend contracts (DTOs + generated OpenAPI). Code comments, error messages, commit messages, and PR descriptions are written in **Portuguese (pt-BR)**.

Roadmap (README): auth, inspector profiles, listings, the listing lifecycle, appointment scheduling up to AWAITING_PAYMENT and the expiry job (PR C), the error contract (`code` on every error) and the front-facing contract (explicit operationIds, named enums, paginated `GET /inspectors`, `roles` on `/auth/me`) are done. Next up: payment/escrow, then inspection reports/reviews, then proximity search (PostGIS). [docs/ai-tooling-plan.md](docs/ai-tooling-plan.md) lists the planned AI agents and skills, and in doing so mentions future domain concepts such as an appointment state machine, escrowed payments with commission in cents, and role-specific response DTOs.

Known risks and their status (open, accepted, resolved) live in [docs/audit.md](docs/audit.md). Read it before designing, reviewing, or testing, and update it when a change resolves or introduces a risk.

```bash

npm run start:dev             # API on http://localhost:3000, Swagger at /docs, JSON at /docs-json

```

**Windows gotcha (port 3000):** stopping the task that ran `npm run start:dev` can leave the child Node process (`node --enable-source-maps ...\dist\main`) still listening on port 3000. If the port stays busy, find the owner with `Get-NetTCPConnection -LocalPort 3000 -State Listen` (the `OwningProcess` column), confirm it is the process you started (e.g. `Get-CimInstance Win32_Process -Filter "ProcessId=<pid>"` for its command line and start time), and stop only that PID. Never kill every `node.exe`: the user may have their own `start:dev` running.

**Node and npm versions** live only in `devEngines` in `package.json`: Node `^24.0.0` and npm `12.2.1` exact, both with `onFail: "error"`, so every `npm run` fails on another version (`EBADDEVENGINES`). Node 24 bundles npm 11; install the declared npm globally on top of it (`npm i -g npm@12.2.1`, check with `npm -v`). The CI reads both versions from there, so updating the local npm (or Node major) means updating `devEngines` in a `chore` commit first (and the versions quoted in this paragraph); never write a version in the workflow. The CI installs npm only from an exact `x.y.z` there.

**Installing from scratch:** `npm ci` then the e2e database (see Testing). npm 12 blocks dependency install scripts that aren't in `allowScripts` in `package.json`; there, `bcrypt`, `prisma`, `@prisma/engines` and `@scarf/scarf` are denied (`false`) on purpose (risk 63 in the audit): `bcrypt` ships N-API prebuilds, the Prisma CLI downloads the schema engine on first use (so the first `prisma` command needs network or the user's engine cache), and scarf is telemetry. The project's own `postinstall` (`prisma generate`) still runs. When a new dependency with an install script appears, `npm install-scripts ls` lists it: review what the script does and approve it pinned (`npm install-scripts approve <pkg>`) or deny it, never `--dangerously-allow-all-scripts`. Never run `npm audit fix --force`.

**Before `npm ci`, `npm install`, or anything else that deletes or rewrites `node_modules`:** list the project's node processes with their command lines (`Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Where-Object { $_.CommandLine -match 'carcheck-api' } | Select-Object ProcessId, CreationDate, CommandLine`). If any is running, STOP and ask the user to stop it; never kill a user's process. On Windows a running app holds native files open (e.g. `bcrypt.node`), and `npm ci` then fails with EPERM halfway through, leaving `node_modules` partly deleted.

Env vars (`.env`, see `.env.example`): `DATABASE_URL`, `JWT_SECRET` (required, `getOrThrow`), `JWT_EXPIRES_IN_SECONDS` (default 3600). Business rules are validated at boot by `validateEnv` ([src/config/env.validation.ts](src/config/env.validation.ts)) and injected with `@Inject(BUSINESS_RULES)`: `PLATFORM_FEE_BPS` (**required**, integer 0..10000), `MIN_INSPECTION_PRICE_CENTS` (default 5000, at most `INSPECTION_PRICE_MAX_CENTS` = 500000, the `basePriceCents` cap), `APPOINTMENT_DURATION_MINUTES` (default 60), `APPOINTMENT_MIN_NOTICE_HOURS` (default 24). `JOBS_ENABLED` (boolean `true`/`false`, default `true`, also validated by `validateEnv`) turns the scheduled jobs on or off: with `false`, `JobsModule` (`ScheduleModule` + the `@Cron` classes) is not loaded (`ConditionalModule.registerWhen`, read with `isJobsEnabled`). `DOCS_ENABLED` (same parsing, default `true`; turn it off in production) decides in `configureApp` (`isDocsEnabled(process.env)`) whether `SwaggerModule.setup` runs: with `false`, `/docs`, `/docs-json` and the assets fall into the route 404. `npm run openapi` never goes through `configureApp`, so `openapi.json` does not depend on it (the spec generates it with `DOCS_ENABLED=false`). The e2e config sets `PLATFORM_FEE_BPS` and `JOBS_ENABLED=false`.

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs on PRs to `main` with the Node and npm of `devEngines` (risk 64): `setup-node` reads Node from `package.json` with the npm cache off (`package-manager-cache: false`, no `cache`), a step installs the declared npm from `${{ runner.temp }}` and another fails if `npm -v` differs. The runner's npm 11 enforces `devEngines` even in commands like `npm config get cache`, so no step may run npm inside the project folder before npm 12.2.1 is installed (that is what the setup-node cache did); don't assume only `npm run` checks `devEngines`. Then `npm ci` with `NPM_CONFIG_STRICT_ALLOW_SCRIPTS=true` (a dependency with an install script outside `allowScripts` fails the install), `npm install-scripts ls --json` must return an empty list, `npm audit signatures` checks registry signatures and attestations, then a step that runs the permissions spec alone (`./node_modules/.bin/vitest run --config test/claude/vitest.claude.config.ts` with the JSON reporter, never `npx`, then a `node` check that fails unless `success`, `numTotalTests > 0` and `numPassedTests === numTotalTests`, so an excluded, empty or skipped spec fails the job; it runs before lint, build and the unit tests so none of them can touch the workspace first, though the `postinstall` of `npm ci` still runs before it; risk 57, item G), then `npm run lint`, `npm run build`, `npm test`, `prisma migrate deploy` and `npm run test:e2e` against a PostGIS service container. The job id `build` is the status check required by the `main-protection` ruleset: never rename it, give it a `name:` or a matrix. The job has `timeout-minutes: 20` and `CHECKPOINT_DISABLE=1` (Prisma CLI telemetry off), and a `concurrency` group per workflow + ref cancels the previous run of the same PR. The workflow has `permissions: contents: read`, checkout with `persist-credentials: false`, and actions pinned by the tag's commit SHA with the version in a comment (verify a new SHA with `gh api repos/<owner>/<repo>/git/ref/tags/<tag>`, following an annotated tag to its commit; risk 79). Unit tests must still not need a live DB.

## Architecture

- **ESM + NodeNext**: `"type": "module"`. Every relative import must end in `.js` (`import { X } from './x.service.js'`). Use `import type` for type-only imports (e.g. `JwtPayload`, Prisma `Role`/`Prisma` types), since `isolatedModules` is on.
- **Prisma 7**: the schema is [prisma/schema.prisma](prisma/schema.prisma) and the CLI config (datasource URL, migrations path) is [prisma7.config.ts](prisma7.config.ts). The client is generated into `src/generated/prisma/` (gitignored) and imported from `../generated/prisma/client.js`, which also provides enums like `Role` and `ListingStatus`. `PrismaService` ([src/prisma/prisma.service.ts](src/prisma/prisma.service.ts)) extends `PrismaClient` with the `@prisma/adapter-pg` driver adapter and is exported by a `@Global()` `PrismaModule`. `prisma/prisma.module.ts` and `prisma/prisma.service.ts` are empty leftover files; the real ones are under `src/prisma/`.
- **`prisma migrate dev` does not regenerate the client** in Prisma 7: run `npx prisma generate` after it (see the `prisma-migration-workflow` skill).
- **Money** is stored as integer cents (`priceCents`, `basePriceCents`).
- **Global `ValidationPipe`** in [src/main.ts](src/main.ts) uses `whitelist`, `forbidNonWhitelisted`, and `transform`. Unknown fields are rejected, and query-string numbers need `@Type(() => Number)` (see `ListListingsQueryDto`).
- **`helmet`** is the first thing in `configureApp` ([src/app.setup.ts](src/app.setup.ts)), with the default CSP for the whole API, `/docs` included, and `x-powered-by` disabled. Anything registered on Express before it (middleware, `SwaggerModule.setup`) misses the headers, so new middleware goes after it. Don't loosen the CSP globally to fix the Swagger UI; if needed, loosen it only on `/docs` (risk 58 in the audit).
- **Shutdown**: `PrismaService` calls `$disconnect` in `onApplicationShutdown` (Nest's last hook, after crons stop and HTTP closes); that is what closes the adapter-pg pool. `app.enableShutdownHooks()` lives only in `main.ts`, not in `createApp`, so the e2e don't pile up signal listeners. `app.close()` alone leaves no DB connections.
- **Transaction conflicts** (deadlock 40P01, serialization failure 40001, Prisma P2034) become 409 `TRANSACTION_CONFLICT` "Conflito ao processar, tente novamente" in the global filter, logged with `Logger.warn` (code + route pattern, no ids). Detect them with `transactionConflictCode` ([src/common/prisma/prisma-errors.ts](src/common/prisma/prisma-errors.ts)); with adapter-pg a raw query reports P2010, so match on the SQLSTATE. Don't add ad hoc retry loops around `$transaction`: the API contract is "409 = retry". `test/prisma-driver-contract.e2e-spec.ts` forces a real deadlock to pin the error format.
- **Error contract.** Every error response is an `ErrorResponseDto` (`statusCode`, `code`, `error`, `message`, `errors?`, `path`, `timestamp`), `application/json`, with `Cache-Control: no-store` (set by the `AllExceptionsFilter` after it strips file headers). The front decides by `code`, never by the pt-BR `message`.
  - **Codes** live only in the `ErrorCode` enum ([src/common/errors/error-code.ts](src/common/errors/error-code.ts)), SCREAMING_SNAKE_CASE, value equal to the name; it is the named enum `ErrorCode` in OpenAPI. A domain error is thrown with the code at the throw site: `throw new ConflictException(withCode(ErrorCode.INVALID_STATE, 'Ação não permitida no estado atual'))` (the Nest exception keeps `.message`, so specs asserting the text still work). An `HttpException` without a code gets the status default (`defaultCodeForStatus`: 400 `BAD_REQUEST`, 401 `UNAUTHENTICATED`, 403 `FORBIDDEN`, 404 `NOT_FOUND`, 409 `CONFLICT`...); a code in the body that is not in the enum is ignored. **New code:** add it to the enum, throw it with `withCode`, run `npm run openapi`, and cover it in `test/error-codes.e2e-spec.ts` (generic) or `test/error-codes-domain.e2e-spec.ts` (domain). After PR #20, **never remove or rename a code, only add** (new codes go at the end of their group; a code that stops being emitted stays in the enum). The enum is open: the `code` description tells the front to handle an unknown code by the HTTP status. The same add-only rule holds for the open response enums `AppointmentStatus`, `AppointmentAction`, `AppointmentActor` and `Role` (see Named enums below): only add values, never remove or rename one. Never put a loose code string in a throw.
  - **Messages of the HTTP layer** (Express router, body-parser, assets, the route 404, the 415 middleware and `parseIdPipe`) live only in [src/common/http/http-error-messages.ts](src/common/http/http-error-messages.ts). The filter keeps its database messages (`PRISMA_ERROR_MAP`, exclusion violation, transaction conflict) and the guards keep theirs (`INVALID_TOKEN_MESSAGE` in `jwt-auth.guard.ts`). Errors from the Express layer (router, body-parser, static assets) never reach the client with their own message: it is English and may echo the input. Recognized body-parser errors (`BODY_PARSER_ERROR_TYPES`) get code and message in the filter by `type` (`BODY_PARSER_ERRORS`); whatever Nest's `mapException` turns into an `HttpException` gets a fixed pt-BR message by status in `AppExpressAdapter` (`HTTP_LAYER_MESSAGES`, fallback "Requisição inválida") and the status default code. A new case gets a map entry, never `error.message`.
  - **Route not found**: `AppExpressAdapter.setNotFoundHandler` replaces Nest's handler (which throws `Cannot GET <url>`) with a 404 `ROUTE_NOT_FOUND` "Rota não encontrada", without echoing the URL. Service 404s keep their own code and message.
  - **`:id` params** use `@Param('id', parseIdPipe)` ([src/common/validation/parse-id.pipe.ts](src/common/validation/parse-id.pipe.ts)), never a bare `ParseUUIDPipe`: 400 `INVALID_ID` "Identificador inválido".
  - **415 before authentication**: `rejectUnsupportedContentType` runs right after helmet, before the parsers and routing. A request with a body (`Content-Length > 0` or `Transfer-Encoding`) whose `Content-Type` is not in `ACCEPTED_BODY_CONTENT_TYPES` ([src/common/limits.ts](src/common/limits.ts): JSON and urlencoded; add `multipart/form-data` there together with its parser when uploads come) gets 415 `UNSUPPORTED_MEDIA_TYPE`, even without a token (415, not 401). It only calls `next(err)`, so the response goes through the filter. A POST without a body passes.
  - **Headers already sent** (e.g. a `/docs` asset failing mid-stream): the filter logs with `Logger.error` and calls `response.destroy()`, never `json()`.

### Feature module pattern (`src/<feature>/`)

`<feature>.module.ts`, `.controller.ts`, `.service.ts`, and a `dto/` folder. Follow `listings/` as the reference:

- **Request DTOs** use `class-validator` plus `@ApiProperty`. Update DTOs extend `PartialType` from `@nestjs/swagger`, not `@nestjs/mapped-types`.
- **Response DTOs** never expose Prisma entities. Each one has a `static from(entity)` mapper, and services return these DTOs. Controllers declare return types and `@ApiOkResponse`/`@ApiCreatedResponse` plus error responses (`@ApiNotFoundResponse`, `@ApiForbiddenResponse`, etc.), because the OpenAPI contract is generated from code, never written by hand.
- **The Swagger describes what the API really does, errors included.** Helpers in [src/common/swagger/api-responses.ts](src/common/swagger/api-responses.ts): `@ApiCommonErrorResponses()` on every controller class (429 of the global throttler and 500), `@ApiBodyErrorResponses()` on every route with a body (413, 415; the route still declares its own 400), `@ApiUuidParam()` on every `:id` route (plus a 400 `INVALID_UUID_DESCRIPTION`); every authenticated route documents 401, and routes with a transaction mention `TRANSACTION_CONFLICT_DESCRIPTION` in the 409. Integer fields use `type: 'integer'` (no schema may be `type: number`), ids `format: 'uuid'`. Never put a value that changes by date or environment in a schema (e.g. the vehicle year has no `maximum`, the rule goes in the description): `openapi.json` must be deterministic. `test/openapi-contract.e2e-spec.ts` enforces these rules.
- **`openapi.json`** (repo root) is the versioned contract the front generates types from, built by `buildOpenApiDocument` ([src/openapi/openapi-document.ts](src/openapi/openapi-document.ts)), the same function behind `/docs-json`. **Changed an endpoint or a DTO → run `npm run openapi` and commit `openapi.json` in the same commit.** The unit test `src/openapi/openapi.spec.ts` (`toMatchFileSnapshot`) fails when the file is stale; with `CI=true` it also fails when the file is missing, instead of writing it.
- **operationId**: every route declares one with `@ApiOperationId('<verb><Resource>')` ([src/common/swagger/api-responses.ts](src/common/swagger/api-responses.ts)), camelCase, decoupled from the method name (it's the function name in the front's generated client, so renaming a controller method must not change it). Shape `<verb><Resource><Complement?>`. Verbs: `list` for collections, `get` for one item, `create`, `update`, and the domain verb for intent routes (`pauseListing`, `markListingSold`, `acceptAppointment`, `archiveListing` for the `DELETE` that archives). `My` only when the same resource also has a public version (`listMyListings`, `getMyInspectorProfile`); a private resource that is always the caller's doesn't take it (`listAppointments`). Nested collections are `list<Parent><Children>` (`listInspectorReviews`); a sub-resource route that is a state-machine action uses the action verb (`submitAppointmentReport`). Auth routes are the named exceptions (`registerUser`, `login`, `getCurrentUser`). Routes that aren't for the front (e.g. a payment webhook) take `@ApiExcludeEndpoint()` and stay out of the document. A route without it gets the sentinel `MISSING_OPERATION_ID_<Controller>_<method>` from the `operationIdFactory` in `buildOpenApiDocument`; `test/openapi-contract.e2e-spec.ts` rejects it, rejects duplicates and pins the full table. **New route → new operationId, added to that table.** Never change an existing one.
- **Named enums**: every enum in a DTO has `enumName` (`@ApiProperty({ enum: X, enumName: 'X' })`, the name of the Prisma enum when there is one), so it is a single `components.schemas` entry referenced by `$ref`, never copied inline. The only inline enums allowed are the one-value literals of a discriminator property (`myRole` in each appointment variant); the contract test checks that exception applies to nothing else, and that every enum schema is referenced. **New enum → `enumName` + add it to `NAMED_ENUMS` in the contract test + a neutral description in `NAMED_ENUM_DESCRIPTIONS` ([src/openapi/enum-descriptions.ts](src/openapi/enum-descriptions.ts)).** `@nestjs/swagger` copies the description of the first field that registers an enum into the enum schema, so `buildOpenApiDocument` overwrites it from that map; each field keeps its own description. **Open response enums** (`AppointmentStatus`, `AppointmentAction`, `AppointmentActor`, `Role`, like `ErrorCode`): their description ends with `OPEN_ENUM_NOTE` ("A lista pode crescer; trate valor desconhecido sem quebrar."), and the same rule as `ErrorCode` applies: **only add values, never remove or rename one**. A non-array enum property comes out as `allOf: [{ $ref }]` (that's how `@nestjs/swagger` emits it); a nullable one keeps `nullable: true` beside the `allOf`.
- **Unions** (`oneOf`) aren't classes, so Nest doesn't register them: `buildOpenApiDocument` adds them to `components.schemas` (today only `AppointmentResponseDto`, from `appointmentResponseSchema()`), and routes reference them with `appointmentResponseRef()`, never an inline `oneOf`.
- **UF (`state`)**: inputs use `@BrazilianStateField()` (trim + uppercase, `@IsIn` of the 27 UFs), responses `@ApiBrazilianState()`; both point to the `BrazilianState` schema ([src/common/validation/brazilian-state.ts](src/common/validation/brazilian-state.ts)). The DB column stays `String` (no enum, no CHECK).
- **Input limits** live only in [src/common/limits.ts](src/common/limits.ts): every DTO string has a `@MaxLength` and every number a `@Max` (below the 32-bit `Int` of the columns, otherwise Postgres rejects it with a 500), and the same constant goes into `@ApiProperty({ maxLength, maximum })`, so the limit is in the OpenAPI contract (exception: the vehicle year, whose ceiling changes every year, has no `maximum`; see the Swagger rule above). Never repeat the number in the DTO, nor in a Swagger description: interpolate the constant. The password at registration is also measured in UTF-8 bytes (`@MaxBytes`, bcrypt's 72-byte limit); login doesn't measure bytes. Arrays get `@ArrayMaxSize`; use `@UniqueArray` ([src/common/validation/](src/common/validation/)) instead of class-validator's O(n²) `@ArrayUnique`. The JSON/urlencoded body limit (100kb) is set explicitly in `configureApp`.
- **Pagination** returns `{ items, total, page, limit }`, with `limit` capped (max 50), using `$transaction([findMany, count])`. `page` is capped too (`GET /listings`, `GET /listings/mine` and `GET /inspectors`, all via `PageQueryDto` in [src/common/dto/page-query.dto.ts](src/common/dto/page-query.dto.ts): `PAGE_MAX` = 200, so `skip` never exceeds 10,000 rows; `GET /appointments` has its own DTO). The route documents the 400 with `PAGINATION_RULE`. Each page has its own response DTO (`PaginatedListingsResponseDto`, `PaginatedInspectorsResponseDto`...), since Swagger has no generics. The `orderBy` needs a unique tie-breaker (`[{ createdAt: 'desc' }, { id: 'desc' }]`, `STABLE_ORDER` in each service), otherwise rows with the same `createdAt` can repeat or vanish between pages.
- **Ownership (404 vs 403)** depends on whether the resource is public or private (see the `ownership-check` skill):
  - **Public resource** (anyone may know it exists, e.g. listings): 404 when it doesn't exist; **403** when it exists but the caller isn't the owner. Services use a private `assertOwner(id, userId)`.
  - **Private resource** (only participants may know it exists, e.g. appointments, payments): **404** both when it doesn't exist and when the caller isn't a participant, so existence isn't leaked. A participant whose role can't perform an action gets 403.
  - Public reads filter by visibility in the `where` (e.g. `status: 'ACTIVE'`), never after fetching.

### Listing lifecycle ([src/listings/](src/listings/))

- Status changes only through intent routes, never through `PATCH`: `POST /listings/:id/pause` (ACTIVE→PAUSED), `/activate` (PAUSED→ACTIVE), `/mark-sold` (ACTIVE|PAUSED→SOLD) and `DELETE /listings/:id`, which **archives** (→ARCHIVED, 204) instead of deleting. `ARCHIVED` is final; `SOLD` only goes to `ARCHIVED`. The rules live in the pure function `decideListingTransition` ([src/listings/listings.state-machine.ts](src/listings/listings.state-machine.ts)), applied with `updateMany` filtered by the status that was read (409 on invalid transition or race). Never delete a listing physically.
- `UpdateListingDto` has no `status` (sending it is a 400 through the whitelist). `PATCH` on an archived listing is a 409, enforced in the `update` `where` (`status: { not: 'ARCHIVED' }`).
- Archived listings are hidden from `GET /listings`, `GET /listings/:id` and `GET /listings/mine`.
- Public responses (`ListingResponseDto`) carry neither `sellerId` nor `status`; owner routes (`POST`, `GET /mine`, `PATCH`, transitions) return `MyListingResponseDto` (public fields + `status`, still no `sellerId`). `GET /listings/mine` is paginated (`PaginatedMyListingsResponseDto`).
- The appointment design that builds on this is in [docs/appointments-design.md](docs/appointments-design.md).

### Appointments ([src/appointments/](src/appointments/))

Design: [docs/appointments-design.md](docs/appointments-design.md). The flow ends at `AWAITING_PAYMENT`; `PAID`, `REPORT_SUBMITTED`, `DISPUTED` and `COMPLETED` exist in the enum and the transition table but no route reaches them.

- **Private resource**: non-participants get 404 ("Agendamento não encontrado"); a participant whose role can't act gets 403; wrong state gets 409. Only `JwtAuthGuard` (no `RolesGuard`): the role that matters is the user's role _in that appointment_ (`participantOf`), not the global role.
- **State machine**: pure `decide(actor, action, status)` in [appointments.state-machine.ts](src/appointments/appointments.state-machine.ts); one route per intent (`accept`, `decline`, `confirm`, `cancel`), never a PATCH with status. Writes use `updateMany` filtered by the status read and `expiresAt > now`; `count === 0` is a 409.
- **Deadlines** come from the injectable `CLOCK` ([src/common/clock/clock.ts](src/common/clock/clock.ts)), never the DB `now()`; tests use `FakeClock` (`test/support/fake-clock.ts`). `expiresAt = min(entered state + window, startsAt)` (`deadlineFor`). An action on an expired appointment writes `EXPIRED` **outside** any transaction and then returns 409. The "due" rule (status in `EXPIRABLE_STATUSES` and `expiresAt <= now`) lives only in `isDue`/`dueWhere`/`expiredData` ([appointment-deadlines.ts](src/appointments/appointment-deadlines.ts)); reuse them, don't rewrite the comparison.
- **Expiry job**: `AppointmentExpiryCron` runs every minute and calls `AppointmentExpiryService.expireDue(clock.now())`, a single conditional, idempotent `updateMany` (never `PAID` or later). Tests call `expireDue` directly; the cron class skips overlapping runs and logs errors instead of throwing. Every API instance runs it (safe, see the design doc).
- **Double booking** is prevented in the DB by the exclusion constraint `Appointment_inspector_slot_excl` (only `ACCEPTED`, `AWAITING_PAYMENT`, `PAID` occupy the slot). Its 23P01 reaches the app as P2039/P2010 with the SQLSTATE in `meta.driverAdapterError.cause.originalCode`; `isPgError` detects it and the global filter returns 409 `SLOT_UNAVAILABLE`. The partial unique index `Appointment_open_triplet_key` (`APPOINTMENT_OPEN_TRIPLET_INDEX`) blocks duplicate open requests (P2002, recognized by name with `isUniqueViolationOn`). These constraints and the CHECKs live only in the migration SQL; Prisma ignores them (drift verified). Don't drop them. `accept` starts its transaction by locking the inspector's profile (`SELECT 1 FROM "InspectorProfile" WHERE "userId" = … FOR NO KEY UPDATE`, the weakest mode that conflicts with itself, before the `verified` check), so two overlapping accepts of the same inspector queue up and the loser gets 23P01 (`SLOT_UNAVAILABLE`) instead of a deadlock inside the constraint check (40P01, `TRANSACTION_CONFLICT`; risk 82); don't remove it. Rule (design doc): every write that puts or keeps a row in the constraint set takes that lock as the first statement of its transaction; `accept` and `confirm` follow it, and the future `PAID` transition must too.
- **Money** is frozen at creation (`priceCents`, `platformFeeBps`, `platformFeeCents`, `inspectorPayoutCents`) with the pure `splitPlatformFee` ([src/common/money/platform-fee.ts](src/common/money/platform-fee.ts)): integer half-up, `fee + payout === price`.
- **Responses per role** (`myRole` discriminator; the union is the named schema `AppointmentResponseDto` in OpenAPI): Seller = base (no money), Buyer = base + `priceCents`, Inspector = base + price, fee bps, fee and payout. Forbidden fields don't exist in the response. No response carries user ids.
- Creating locks the listing with `SELECT ... FOR SHARE`; listing transitions (`pause`, `mark-sold`, archive) update the listing first, then cancel open appointments with `endedBy: SELLER` (it's the seller's action; `SYSTEM` is only for expiry), or 409 if one is `PAID`.
- **Advancing state in dev** (no routes for payment/report yet): open `npx prisma studio`, edit the `Appointment` row. The CHECKs still apply: `PAID` needs `meetingAddress` set (and may have `expiresAt` null); `REQUESTED`/`ACCEPTED`/`AWAITING_PAYMENT` need `expiresAt`; `DECLINED`/`CANCELLED`/`EXPIRED` need `endedBy` (and only they may have it). To simulate an expired deadline, set `expiresAt` in the past and call any action. To let an inspector receive requests, set `InspectorProfile.verified = true` there too.

### Auth ([src/auth/](src/auth/))

- JWT payload is `{ sub: userId, email }`. `JwtAuthGuard` verifies the Bearer token and sets `request.user`. `@CurrentUser()` reads it.
- `GET /auth/me` returns `CurrentUserResponseDto` (`UserResponseDto` + `roles`, read from the DB on each request, enum `Role`) with `Cache-Control: no-store`. Register and login keep `UserResponseDto`, without roles. `roles` is for the UI only; authorization is always the server's `RolesGuard`.
- Roles (`USER`, `INSPECTOR`, `ADMIN`) live on `User.roles` (an array) and are **not** in the token. `RolesGuard` with `@Roles(...)` loads them from the DB on each request, so role changes apply right away. Use `@UseGuards(JwtAuthGuard, RolesGuard)` in that order.
- Creating an inspector profile (`POST /inspectors/me`) pushes `INSPECTOR` onto the user's roles inside the same transaction.
- **Inspector verification is manual and intentional for now.** `InspectorProfile.verified` starts as `false` and is set to `true` by hand (e.g. via `npx prisma studio`). No route sets it, and `UpdateInspectorProfileDto` deliberately excludes it. This is a product decision, not a bug: don't "fix" it by adding `verified` to a DTO or creating an endpoint unless asked. `GET /inspectors` lists only verified profiles.
- `AuthModule` exports `JwtModule`, `JwtAuthGuard`, and `RolesGuard`, so feature modules that use the guards import `AuthModule`.

## Conventions

- Branches are `<type>/<name>`, with `<type>` one of `feat`, `fix`, `chore`, `test` or `docs`. Commits use Conventional Commits in Portuguese with a scope, e.g. `feat(listings): adiciona CRUD de anúncios`.
- PRs follow [.github/pull_request_template.md](.github/pull_request_template.md): "O que mudou", "Como testar", and a checklist that includes updating the README roadmap.
- O agente nunca executa comandos que alteram o remoto, com uma única exceção: a skill /ship-pr, quando o usuário a aciona explicitamente. Merge, force push e remoção de branch remota são sempre do usuário.

## Working rules

1. **Stop before going beyond what was approved.** When a change goes beyond what the user approved, or when a task needs a tool or command other than the agreed one (even a read-only one), stop and ask the user first.
2. **Stop when a tool or permission blocks a command.** Ask the user before looking for another way, even if the alternative only reads files.
3. **No approximate counts.** Give the real number, or write "not counted".
4. **Diffs without external programs.** Every command that produces a diff (`git diff`, `git show`, `git log -p` and the like) takes `--no-ext-diff --no-textconv` right after the subcommand.
5. **Survey before coding.** Stop and show the survey to the user before writing code. Search by the literal text (descriptions, error messages, contract texts) as well as by constant and function names.
6. **Commits.**
   - Conventional Commits in pt-BR with a scope.
   - A `test:` commit with the failing test comes before the `fix:`/`feat:`/`chore:` commit. When the test already passes before the change, the proof is a mutation in a copy outside the repository (rule 9).
   - `git add` only specific files, never `-A` or `.`.
   - Message through `git commit -F`, from a UTF-8 file without BOM outside `.git/`. In PowerShell 5.1: `[IO.File]::WriteAllText(path, text, (New-Object Text.UTF8Encoding $false))`; redirecting with `>` writes UTF-16.
   - No push (only through `/ship-pr`).
7. **Review by the agents.** Bring every finding with a recommendation for each one, and apply nothing before the user answers.
8. **Full suite after the last commit:** `npm run lint`, `npx tsc --noEmit`, unit tests (`npm test`) and e2e tests (`npm run test:e2e`).
9. **Mutations in a copy outside the repository.**
   - `robocopy` the project to the session scratchpad, excluding `node_modules`, `.git`, `.claude` and `.env`. If a mutation run needs `.env` (e2e tests, for example), stop and ask.
   - The user creates the `node_modules` junction.
   - The user brings the files of `.claude/` and of the permissions spec folder.
   - Before each text replacement, confirm the snippet is unique (count = 1, reading with `Get-Content -Encoding UTF8`).
   - After reverting, the `git hash-object` of the file in the copy must equal `git rev-parse HEAD:<file>`.
   - Each mutation must break exactly one test.
   - The user removes the copy.
10. **Final report, in a fixed format:** the branch's `git log`; tests before vs after (real counts); the diff of the specs, with what replaces each removed line; the reviewers' findings; the result of each mutation; what was not verified. Paste every output into the report; never refer to output "above" without showing it.

- **E2E tests** live in `test/**/*.e2e-spec.ts` and run with `npm run test:e2e`. They boot the full `AppModule` against a **separate database, `carcheck_test`**, never the dev database `carcheck`:
  - Create it once: `docker compose exec -T db psql -U app -d carcheck -c "CREATE DATABASE carcheck_test"`. The global setup (`test/support/global-setup.ts`) refuses any URL whose database is `carcheck` or does not end in `_test`, then runs `prisma migrate deploy` on it.
  - `vitest.config.e2e.ts` sets `DATABASE_URL` (override with `E2E_DATABASE_URL`) and a test-only `JWT_SECRET`, and runs one file at a time because the files share the database.
  - Create the app with `createTestApp()` from `test/support/test-app.ts` (same adapter and `configureApp()` as `src/main.ts`; throttler limits raised 1000x unless `realThrottler: true`). Call `resetDatabase(app)` in `beforeEach` and `closeTestApp(app)` in `afterAll` (it is just `app.close()`; the Prisma connections close in `onApplicationShutdown`). Shared helpers live in `test/support/fixtures.ts` (`ERROR_KEYS` is the key set of the error format). `beforeInit` runs a callback between `configureApp` and `init` (e.g. a test-only Express middleware).
  - CI runs them against a Postgres service container, after the unit tests.
- Test names are in pt-BR and describe behavior (`it('retorna 403 quando o anúncio é de outro usuário')`). One behavior per `it`; assert the exception type and message, not just "it threw".
- **Tests are the specification.** When a test fails, fix the production code. Never edit, comment out, skip (`it.skip`/`it.todo`/`it.fails`) or loosen an existing test just to make it pass; if a test looks wrong, stop and explain why.
- Before adding a case, look in the module's existing spec file and extend it instead of duplicating cases.
- Bug fixes go in two commits: `test(<scope>): ...` with the failing test, then `fix(<scope>): ...` with the fix.
